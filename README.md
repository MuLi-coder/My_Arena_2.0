# My Arena 自走棋 — 第二版

> **版本定位**：这是项目的第二版。相较于 1.0，本版的重要进展不只是继续增加功能，而是开始把“数据模型、游戏规则处理、Qt 展示”之间的接口显式化：管理器对 GUI 提供数据读取和请求入口，控件被拆分为棋盘格/单位/装备及信息面板，行动和坐标也开始使用结构化类型。它仍是持续演进中的原型，接口设计和对象所有权尚未彻底收敛，文中会同时说明成功改进与保留的问题。

## 项目简介

项目使用 C++17、Qt 6 Widgets 和 CMake 构建，是一个桌面自走棋原型。当前代码包含准备区、备战区、商店、装备栏、玩家信息和战斗流程相关组件。`main.cpp` 启动 Qt 应用，创建游戏窗口；游戏状态和核心规则由 `GameManager` 协调，界面通过请求接口发起操作，并通过数据接口获取显示所需信息。

## 技术栈与构建

- C++17
- Qt 6：Core、Widgets、Gui
- CMake 3.16+

```bash
cmake -S . -B build
cmake --build build
```

## 当前架构

### 1. 启动与界面层：`main.cpp`、`GameWindow`

`main.cpp` 创建 `QApplication` 和 `GameWindow`。`GameWindow` 是主界面与输入协调者：持有 `GameManager`，构造棋盘格、备战区、商店、装备栏和按钮；处理鼠标操作及按钮点击；将购买、拖动、升级、刷新、状态切换等意图交给管理器；订阅管理器的信号并刷新界面或显示反馈。

界面控件已经拆分：

- `UnitWidget`、`EquipmentWidget` 分别负责单个单位/装备的视觉呈现。
- `UnitPanel` 用于展示单位详情并发出购买请求。
- `EquipmentPanel` 已有面板类型的占位，但从当前声明看尚未形成完整功能。
- `ParaWidget` 展示玩家参数。

### 2. 应用/流程协调层：`GAME_LOGIC/GameManager`

`GameManager` 是 GUI 与核心游戏对象之间的协调入口。它持有 `PreBoard`、`ComBoard`、`Player`、`Shop` 和 `EquipmentRepo`，管理 `Ready / Prepare / Combat / Resolve` 状态、战斗计时和战斗推进，并向界面暴露：

- **数据接口**：棋盘、备战区、装备、商店和玩家数据的读取接口。
- **请求接口**：状态切换、升级、商店刷新、购买和拖动等带校验的操作入口。
- **信号**：UI 更新、请求失败、状态变化、结算和旅程结束等事件。

这比 GUI 直接改动多个模型的做法更接近“界面提交意图、管理器协调规则、模型保存状态”的结构。但目前管理器仍同时承载状态机、战斗编排、敌人生成、结算等多种职责，属于中心协调器，而非完全拆分的应用服务体系。

### 3. 游戏数据与规则层：`GAME_LOGIC`

- **`PreBoard`**：保存准备阶段棋盘和备战区中的单位引用，提供读取、替换和重置接口。
- **`ComBoard`**：保存战斗棋盘中的单位引用，负责战斗行动循环并返回发生变化的坐标，用于局部 UI 更新。
- **`Player`**：维护 HP、等级、金币和分数，并通过 `PlayerData` 暴露界面所需数据。
- **`Shop`**：区分商店展示单位和已购买单位，负责商店刷新及对应容器操作。
- **`EquipmentRepo`**：区分展示装备与玩家拥有的装备，负责两组装备槽位的管理。

### 4. 实体层：`ENTITY`

- **`Unit`**：定义单位基础属性、战斗动态数据、单位数据快照 `UnitData`、行动决策接口和受击行为；英雄类型继承并实现重置与技能攻击。
- **英雄子类**：当前 CMake 配置列出 Knight、Mage、Assassin 等类型。
- **`Equipment`**：装备基础实体。

实体层提供 `UnitData` 等面向展示的数据结构，使 UI 不必为展示每个属性而依赖大量零散 getter。不过当前控件仍保存 `Unit*` 绑定，因此模型对象与控件之间仍有直接引用关系。

### 5. 公共类型与工具

`Utils.h` 集中定义棋盘行列、备战区大小以及随机数、延时、曼哈顿距离等辅助声明。`Coord`、`Action`、`UnitData` 等结构使坐标、行动和展示数据不再完全依靠字符串或散乱参数传递。

## 相较第一版的成功改进

### 1. GUI 开始通过请求接口操作游戏

第一版中界面回调直接承担金币检查、扣费、棋子放置和装备操作等规则。第二版的 `GameManager` 明确提供 `requestPlayerLevelUp`、`requestShopRefresh`、`requestBuyUnit`、`requestDragUnitFromTo` 等入口，并用失败信号向 GUI 反馈。这是职责分层上的实质性进步：规则校验有了集中落点，界面有机会退回到输入与呈现职责。

**成功点的边界**：从接口定义可确认方向已建立，但不能仅凭接口名称保证所有业务规则都已完全迁入管理器；后续仍应检查 `GameWindow` 回调是否残留重复校验或直接修改实体。

### 2. 读取数据与提交操作的接口更加明确

管理器提供 `getGridData`、`getBenchData`、`getEquipmentData`、`getShopData`、`getPlayerData` 等 UI 数据接口，并有独立请求接口。相较各处直接访问内部容器，这使“展示需要什么数据”和“玩家请求做什么操作”更容易区分，也为未来替换界面或编写逻辑测试创造了条件。

### 3. UI 控件细分，主窗口不必承担所有绘制细节

单位和装备视图拆成 `UnitWidget`、`EquipmentWidget`，单位详情由 `UnitPanel` 展示，玩家参数由 `ParaWidget` 承担。界面分块后，单个控件可以独立维护自己的显示逻辑，主窗口也更容易从重复的绘制代码中解耦。

### 4. 行动协议从字符串走向类型化结构

第一版的行动方向和攻击类型以 `"Left"`、`"CommonAtt"` 等字符串表示。第二版的 `Action` 使用 `Type`、`Movement`、`AttType` 枚举，并以 `Coord` 表达目标位置。这减少拼写错误和字符串比较，提升接口可读性，也为后续编译期检查、测试和扩展打下基础。

### 5. 实体数据可通过快照结构传递

`UnitData` 与 `PlayerData` 把多个展示字段聚合为结构体，界面可以取得一份明确的数据集合。这样比 GUI 逐项拼装实体内部状态更有利于控制展示接口，也减少模型层与显示逻辑的零散耦合。

### 6. 容器职责有所细化

第二版新增 `EquipmentRepo`，并在 `Shop`、装备仓库中区分展示槽和拥有槽；`PreBoard` 与 `ComBoard` 的数据接口也分别围绕准备阶段和战斗阶段组织。相比第一版把不同用途的槽位和职责混在较宽泛的容器中，这让数据归属意图更容易理解。

### 7. 棋盘更新开始支持坐标级反馈

`ComBoard::marchEveryUnit()` 返回变化坐标，管理器的 `shouldUpdateUI` 信号接受坐标列表。这个设计为只更新受影响的控件、降低整屏刷新耦合提供了基础，也让战斗结果与界面刷新之间的通信更具语义。

## 仍未解决的架构问题

第二版是改进，不是最终架构；以下问题从现有接口/实现仍然可见，应在后续版本继续处理：

1. **裸指针所有权仍不清楚**：棋盘、商店、装备仓库及 UI 控件都保存裸指针。`EquipmentRepo` 析构时删除 owned 装备，而展示数组也存储指针；单位在商店、备战区和战斗棋盘间转移的所有权规则需要明确。请求接口的存在并没有自动解决生命周期问题。
2. **边界检查有风险**：`EquipmentRepo` 的槽位检查使用 `pos > 5`，当容器大小为 5 时，合法下标应为 `0..4`，因此 `pos == 5` 仍会越界。其他容器也应统一检查坐标、槽位、空位和重复引用。
3. **管理器仍偏大**：状态机、计时、战斗流程、敌人生成、购买/拖拽请求和结算仍集中在 `GameManager`。它已经成为更清晰的入口，但还不是低耦合的协调层。
4. **模型和视图仍直接耦合**：`UnitWidget` 持有 `Unit*`，`UnitPanel` 绑定单位指针。若单位被销毁或转移而 UI 没及时刷新，引用可能失效；可考虑只传不可变 `UnitData`，或以稳定 ID 查找数据。
5. **DTO 与实体数据职责需进一步明确**：`UnitData` 同时有实体属性、战斗状态和 UI 字段。它是展示快照、存档格式还是通用数据传输对象，需要明确，避免成为所有层共用的“万能结构”。
6. **部分接口仍使用弱类型/待实现项**：状态请求以外，`changeTimerState(std::string)`、结算 `std::string` 等字符串接口仍存在；`requestLoad()`、`requestSave()` 标注为 TODO。可以改为枚举/结果类型，并补齐完整存档错误处理。
7. **工程组织和验证仍需加强**：当前 CMake 将源文件逐项罗列是可工作的做法，但项目尚需自动化测试、资源打包和跨平台构建验证。仓库内的构建目录不应作为源码依赖。

## 后续建议

- 为单位与装备确定单一所有权策略，优先使用 `std::unique_ptr` 管理拥有关系；跨容器移动通过受控转移接口完成，非拥有关系使用明确的观察指针或稳定 ID。
- 将 `GameManager` 中的战斗引擎、商店/经济规则、存档和阶段流转继续拆分；管理器只保留流程编排。
- 统一所有容器的索引和坐标校验，使用大小常量或 `size()`，避免魔法数及 `>` / `>=` 错误。
- 使用强类型枚举和结果对象替代字符串状态；所有请求应返回明确成功/失败原因。
- 明确数据快照的用途，并使 UI 尽量读取不可变数据，而不是长期持有领域实体裸指针。
- 增加棋盘边界、购买/拖拽失败回滚、商店/装备转移、战斗行动及存档的单元测试。
